## Falhas encontradas e correções aplicadas

### 1. 🔴→✅ Vazamento cross-org em `GET /orgs/:orgId/members` (corrigido)
**Achado:** todos os use-cases de org checavam `isOwner`/membership, **exceto**
`ListMembersUseCase`, e o controller chamava `listMembers.execute(orgId)` **sem o usuário** →
qualquer autenticado listava membros de **qualquer** org. Confirmado empiricamente (token da
Helena's Ink retornava o membro de uma org rival).
**Correção:** `@UseGuards(OrgMembershipGuard)` no método `getMembers`
(`modules/organizations/interface/orgs.controller.ts`), reutilizando o guard já usado em
materials/customers.
**Re-verificado:** org rival → **403**; própria org → **200** (sem regressão).

### 2. 🟡→✅ Campo `city` ausente em clientes (adicionado)
**Achado:** spec 03 define campos núcleo **Nome, Telefone, E-mail, Cidade, Origem**; faltava `city`.
**Correção (full-stack):** coluna `customers.city` (migração `0002_nice_the_order` + `.down.sql`),
`customer.entity.ts`, DTOs, mapper, repository; frontend `types`, `client.schemas`,
`customer-form` (campo Cidade) e `clients-page` (submit). **Type-check verde** nos dois apps.
**Re-verificado:** API cria/lê `city`; o form mostra o campo "Cidade".

> ⚠️ A migração não pôde ser aplicada por `pnpm db:migrate` (ver finding 3); a coluna foi
> adicionada por SQL direto (`ALTER TABLE ... ADD COLUMN IF NOT EXISTS city text`). A migração
> `0002` fica versionada para quando o tracking for corrigido.

## Findings / gaps residuais (follow-ups — NÃO corrigidos nesta rodada)

### 3. 🟠 Migration tracking dessincronizado (devops)
`pnpm --filter backend db:migrate` **falha**: tenta reaplicar `0001` (`CREATE TYPE
stock_movement_type`) que já existe — a tabela `drizzle.__drizzle_migrations` não reflete o
estado real do banco (schema aplicado sem registrar, provavelmente via `db:push`/reset).
**Recomendação:** "baselinar" o tracking (marcar 0000/0001/0002 como aplicadas) ou recriar o
banco via `db:migrate` do zero. Bloqueia migrações futuras pela ferramenta até ser resolvido.

### 4. 🟠 RLS não habilitada (segurança — ADR-0005 marcado como pendente)
Hoje o isolamento entre orgs depende **apenas** da camada de aplicação (`OrgMembershipGuard` +
checagens nos use-cases). Sem RLS, um bug futuro de escopo vira vazamento. **Recomendação:**
habilitar RLS por `org_id` (próxima tarefa de segurança), exigindo contexto de org no acesso ao DB.

### 5. 🟢 Sign-up não atômico (menor)
`SignUpUseCase` cria o usuário no Supabase Auth e **depois** insere em `public.users`; se o
segundo passo falhar, fica um auth user órfão sem `public.users`. **Recomendação:** compensação
(deletar auth user no erro) ou idempotência no `get-me`.
